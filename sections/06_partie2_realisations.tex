\section{Normalisation des offres via adaptateurs}

Sabre renvoie du SOAP ou du texte brut. Les NDC directs (Air France-KLM, British Airways, Aegean, Turkish) répondent en JSON ou XML, parfois les deux selon l'endpoint. Sans couche commune, le frontend accumulait des branches par transporteur, et chaque nouvelle compagnie recopiait des bugs déjà corrigés ailleurs.

Le listing \ref{lst:sabreadapter} montre \texttt{SabreAdapter.ts} : les payloads arrivent dans \texttt{CanonicalFlightOffer}. Ensuite, recherche et panier ne voient plus qu'une structure TypeScript. Les limites de ce modèle sont décrites plus loin ; ici, c'est surtout ce qui a permis de livrer sans dupliquer les écrans.

\begin{lstlisting}[language=TypeScript, caption={\texttt{SabreAdapter.ts}}, label={lst:sabreadapter}]
export interface SabreFlightLeg {
  origin: string;
  destination: string;
  departureDateTime: string;
  arrivalDateTime: string;
  carrierCode: string;
  flightNumber: string;
  cabinClassCode: string; // 'Y', 'J', 'F', 'W', etc.
  bookingClass: string;
  operatingCarrier?: string;
}

export interface SabreAncillaryService {
  serviceId: string;
  serviceType: 'BAGGAGE' | 'SEAT' | 'MEAL' | 'PRIORITY';
  commercialName: string;
  amount: number;
  currency: string;
  segmentRefIds: string[];
}

export interface CanonicalFlightOffer {
  offerId: string;
  provider: 'SABRE_GDS' | 'SABRE_NDC';
  validatingCarrier: string;
  segments: Array<{
    id: string;
    origin: string;
    destination: string;
    departure: string;
    arrival: string;
    airline: string;
    flightNumber: string;
    cabin: 'ECONOMY' | 'PREMIUM' | 'BUSINESS' | 'FIRST';
  }>;
  ancillaries: SabreAncillaryService[];
  pricing: {
    baseFare: number;
    taxes: number;
    total: number;
    currency: string;
    taxBreakdown: Record<string, number>;
  };
}

export class SabreAdapter {
  public static mapCabin(code: string): 'ECONOMY' | 'PREMIUM' | 'BUSINESS' | 'FIRST' {
    const mapping: Record<string, 'ECONOMY' | 'PREMIUM' | 'BUSINESS' | 'FIRST'> = {
      'Y': 'ECONOMY', 'M': 'ECONOMY', 'K': 'ECONOMY', 'L': 'ECONOMY',
      'W': 'PREMIUM', 'E': 'PREMIUM',
      'J': 'BUSINESS', 'C': 'BUSINESS', 'D': 'BUSINESS',
      'F': 'FIRST', 'P': 'FIRST'
    };
    return mapping[code.toUpperCase()] || 'ECONOMY';
  }

  public static normalizeFlightOffer(raw: any): CanonicalFlightOffer {
    if (!raw?.id || !Array.isArray(raw?.flights)) {
      throw new Error("[SabreAdapter] Payload invalide : " + String(raw?.id));
    }

    const segments = raw.flights.map((leg: SabreFlightLeg, idx: number) => ({
      id: 'SEG_' + (idx + 1),
      origin: leg.origin,
      destination: leg.destination,
      departure: leg.departureDateTime,
      arrival: leg.arrivalDateTime,
      airline: leg.carrierCode,
      flightNumber: leg.carrierCode + leg.flightNumber,
      cabin: this.mapCabin(leg.cabinClassCode)
    }));

    const taxDetails: Record<string, number> = {};
    if (Array.isArray(raw.taxes)) {
      raw.taxes.forEach((tax: { code: string; amount: number }) => {
        taxDetails[tax.code] = (taxDetails[tax.code] || 0) + Number(tax.amount);
      });
    }

    return {
      offerId: String(raw.id),
      provider: raw.isNdc ? 'SABRE_NDC' : 'SABRE_GDS',
      validatingCarrier: raw.validatingCarrier || raw.flights[0].carrierCode,
      segments,
      ancillaries: (raw.services || []).map((srv: any) => ({
        serviceId: srv.id,
        serviceType: srv.type || 'BAGGAGE',
        commercialName: srv.name || 'Service Optionnel',
        amount: Number(srv.price?.total || 0),
        currency: srv.price?.currency || 'EUR',
        segmentRefIds: srv.flightRefs || []
      })),
      pricing: {
        baseFare: Number(raw.pricing?.baseFare || 0),
        taxes: Number(raw.pricing?.totalTax || 0),
        total: Number(raw.pricing?.totalAmount || 0),
        currency: raw.pricing?.currency || 'EUR',
        taxBreakdown: taxDetails
      }
    };
  }
}
\end{lstlisting}

\section{Terminal cryptique pour billettistes}

Pendant longtemps, j'ai sous-estimé l'importance de ce morceau. Pour quelqu'un qui n'a jamais travaillé en agence, une interface graphique semble suffire. En réalité, plusieurs billettistes avec qui j'ai échangé vont plus vite en tapant une commande Sabre qu'en enchaînant des clics, surtout lorsqu'il s'agit de manipuler un PNR hors du parcours standard (profil d'imprimante, classe précise, correction d'un champ).

Plutôt que de les renvoyer vers un émulateur externe, j'ai intégré une modale de terminal dans Metis Connect (figure \ref{fig:metis_cryptique}). \texttt{api-aerial} relaie la saisie via l'API Sabre Command et affiche le texte brut renvoyé. Ce n'est pas le composant le plus spectaculaire du projet, mais c'est l'un de ceux qui ont le plus réduit les frictions au quotidien pour une partie des utilisateurs.

\section{Segments passifs Amadeus et Sabre}

Un billet émis en NDC direct est enregistré chez le transporteur, hors inventaire actif du GDS de l'agence. Pourtant, pour que Gestour, IEnterprise ou l'équivalent génère la facture et les flux de trésorerie, un \textbf{segment passif} informatif doit être posé dans le GDS de référence de l'agence.

Une mauvaise coordination produit des doubles écritures passives, ou des écritures incohérentes, ensuite sanctionnées par des avis de débit (\textit{Agency Debit Memos} / ADM). Ce n'est pas théorique : le montant peut atteindre plusieurs milliers d'euros par dossier, et le transporteur n'attend pas que l'on ait fini de déboguer.

La migration \texttt{split-passive-segment-options} isole les paramètres d'écriture par point de vente. Avant notification, le contrôleur vérifie le canal d'émission : dossier traité sur Sabre $\Rightarrow$ écriture passive Amadeus désactivée. Ça coupe le cas le plus fréquent. Ça ne dit rien des ERP qui refusent ensuite la ligne pour une raison de format.

\section{Synchronisation des PNR}

Les PNR évoluent après émission (changement d'horaire, annulation partielle, ajout de SSR). Quand deux agents ouvrent le même dossier, un refresh GDS mal fusionné peut écraser des données locales. La fonction \texttt{keepOnlyMatchingTravelers} dans \texttt{retrieve.controller.js} ne garde que les voyageurs encore présents côté GDS ; ce n'est pas une synchronisation bidirectionnelle complète, et certains champs annexes restent gérés manuellement.

\section{Appairage des passagers avant OrderCreate}

Les XML d'erreur NDC (Air France, British Airways) montraient souvent un détail de saisie : « Éléonore », « D'ALMEIDA », bébé sans siège sans rattachement, bagage accroché à un id fantôme après retrait d'un voyageur. Ce n'était pas toujours le même bug ; c'était souvent le même pipeline d'appairage qui laissait passer un état incohérent.

Le listing \ref{lst:matchespaxrefid} (\texttt{orderCreation.utils.ts}) couvre le nettoyage ASCII, \texttt{associatedAdultRefId} et la purge des services orphelins. Les homonymes, eux, sont restés un trou jusqu'au ticket support décrit plus loin.

\begin{lstlisting}[language=TypeScript, caption={\texttt{orderCreation.utils.ts} --- appairage passagers}, label={lst:matchespaxrefid}]
export interface RawTravelerInput {
  id?: string;
  type: 'ADT' | 'CHD' | 'INF';
  firstName: string;
  lastName: string;
  dateOfBirth?: string;
  assignedAdultIndex?: number; // Requis si type === 'INF'
}

export interface NormalizedPassenger {
  paxRefId: string;
  ptc: 'ADT' | 'CHD' | 'INF';
  givenName: string;
  surname: string;
  birthDate?: string;
  associatedAdultRefId?: string;
}

export function sanitizeIataName(name: string): string {
  return name
    .normalize('NFD')
    .replace(/[\u0300-\u036f]/g, '') // Supprime accents et diacritiques
    .replace(/[^a-zA-Z\s]/g, ' ')   // Remplace tirets et apostrophes par espaces
    .replace(/\s+/g, ' ')           // Reduit les espaces multiples
    .trim()
    .toUpperCase();
}

export function matchesPaxRefId(
  travelers: RawTravelerInput[],
  selectedAncillaries: Array<{ serviceId: string; targetPaxId: string }>
): {
  passengers: NormalizedPassenger[];
  validAncillaries: Array<{ serviceId: string; paxRefId: string }>;
} {
  if (!travelers || travelers.length === 0) {
    throw new Error('[matchesPaxRefId] Aucun voyageur fourni pour la commande');
  }

  const adultRefIds: string[] = [];
  const normalizedPaxList: NormalizedPassenger[] = [];

  // 1. Passe 1 : Traitement et enregistrement des Adultes et Enfants
  travelers.forEach((pax, index) => {
    const generatedRefId = 'PAX' + (index + 1);
    const cleanFirst = sanitizeIataName(pax.firstName);
    const cleanLast = sanitizeIataName(pax.lastName);

    if (pax.type === 'ADT') {
      adultRefIds.push(generatedRefId);
    }

    if (pax.type !== 'INF') {
      normalizedPaxList.push({
        paxRefId: generatedRefId,
        ptc: pax.type,
        givenName: cleanFirst,
        surname: cleanLast,
        birthDate: pax.dateOfBirth
      });
    }
  });

  // 2. Passe 2 : Traitement des Nourrissons (INF) et rattachement adulte
  travelers.forEach((pax, index) => {
    if (pax.type === 'INF') {
      const generatedRefId = 'PAX' + (index + 1);
      const adultTargetRef = adultRefIds[pax.assignedAdultIndex ?? 0] || adultRefIds[0];

      if (!adultTargetRef) {
        throw new Error('[matchesPaxRefId] Nourrisson sans adulte valide : ' + pax.firstName);
      }

      normalizedPaxList.push({
        paxRefId: generatedRefId,
        ptc: 'INF',
        givenName: sanitizeIataName(pax.firstName),
        surname: sanitizeIataName(pax.lastName),
        birthDate: pax.dateOfBirth,
        associatedAdultRefId: adultTargetRef
      });
    }
  });

  // 3. Purge des services ancillaires orphelins
  const validPaxIdSet = new Set(normalizedPaxList.map(p => p.paxRefId));
  const validAncillaries = (selectedAncillaries || [])
    .filter(anc => validPaxIdSet.has(anc.targetPaxId))
    .map(anc => ({ serviceId: anc.serviceId, paxRefId: anc.targetPaxId }));

  return {
    passengers: normalizedPaxList,
    validAncillaries
  };
}
\end{lstlisting}

\chapter{Filtrage multi-compagnies et perfs recherche}
\label{chap:moteur_recherche}

\section{Filtres compagnies et préférences}

En SBT entreprise, les travel managers restreignent souvent les résultats aux alliances contractées (SkyTeam, Star Alliance, Oneworld) ou excluent des low-cost.

\texttt{SelectCompanies.vue} propose deux modes : liste blanche (compagnies conventionnées) et liste noire (transporteurs écartés, reste du marché interrogé).

Les préférences vivent dans Pinia pour la session courante et dans le \texttt{localStorage} du navigateur. Pas d'aller-retour SQL pour un simple réglage d'affichage.

\section{Optimisation des requêtes de recherche}

Le goulot reste la latence des fournisseurs, pas le SQL local. Dans \texttt{api-aerial}, \texttt{createShoppingPayload} (\texttt{shopping.utils.js}) filtre les compagnies exclues \emph{avant} de construire le XML/JSON, pour ne pas interroger tout le monde puis jeter. Sur les recherches complexes, on gagne souvent quelques centaines de millisecondes ; ce n'est pas spectaculaire, mais ça se sent quand trois connecteurs NDC répondent déjà en plusieurs secondes.

Deux autres réglages, sans rapport l'un avec l'autre : un paramètre \texttt{'W'} injecté dans les requêtes Sabre pour privilégier les directs (demande fréquente en voyage d'affaires), et des dates normalisées en ISO 8601 via \texttt{createDepartureWindow} pour que Sabre et NDC interprètent la même fenêtre horaire. Le second a surtout évité des décalages d'un jour sur les fuseaux.

\chapter{Multi-devises et calculs tarifaires}
\label{chap:architecture_financiere}

\section{Devise du point de vente}

Sur le module facturation / conversion, les SQL synchrones qui résolvaient \texttt{agencyCurrency} saturaient le pool dès que plusieurs agences lançaient des recherches en parallèle. On avait un paramètre quasi statique qui bloquait tout le pipeline tarifaire, ce qui n'était pas évident tant qu'on regardait uniquement les temps d'appel Sabre.

J'ai déporté la résolution dans un middleware Express asynchrone, avec un cache mémoire de dix minutes. La devise est lue une fois en tête de requête, injectée dans \texttt{req.context.posCurrency}, puis réutilisée. Une invalidation Redis serait plus réactive ; pour une donnée que les agences changent rarement, le cache local a tenu. Si quelqu'un change la devise d'un POS en journée, il faut encore attendre l'expiration --- on l'a accepté.

\section{Formatage et norme ISO 4217}

Le multi-devises impose ISO 4217. \texttt{formatPrice} et \texttt{OrderRecap.vue} doivent gérer deux décimales (EUR, USD, GBP), zéro (JPY, KRW) et trois (TND, KWD).

Pour les taxes aéroportuaires, l'arrondi bancaire au pair le plus proche (\textit{banker's rounding}) remplace \texttt{Math.round}, qui poussait toujours les demis vers le haut et biaise les totaux sur de gros volumes. On cherche l'égalité entre total facturé et somme des taxes.

\chapter{Back-Office et paramétrage des agences}
\label{chap:backoffice_admin}

\section{Paramétrage des points de vente}

\textbf{\texttt{front-dashboard}} (Nuxt~3, Vuetify~3) sert aux administrateurs à configurer les accès techniques de chaque agence.

On y saisit PCC Sabre (\textit{Pseudo City Code}), Office ID Amadeus et numéro IATA. Par réseau : devise par défaut du POS, marge sur les billets, activation des segments passifs selon les besoins comptables.

\section{Import par lots des profils Sabre}

Les imports massifs de profils voyageurs ont saturé les quotas SOAP Sabre tant que les appels partaient tous en parallèle. Les dialogues \texttt{DialogUpdateSabre.vue} et \texttt{DialogImportProfil.vue} découpent le travail par paquets de 50.

\chapter{Tests et mesures en production}
\label{chap:assurance_qualite}

\section{Tests unitaires et d'intégration}

Les calculs de prix et les flux d'émission sont couverts par des tests sur la CI/CD, surtout là où un écart de centime ou un PaxRefID faux se paie en rejet transporteur.

\texttt{orderCreation.utils.test.js} (Mocha/Chai) exerce \texttt{matchesPaxRefId} sur une quarantaine de cas repris de tickets : bébés multiples, noms à particules, bagages orphelins. \texttt{pricingConsistency.utils.test.js} vérifie $\text{Total} = \text{Base} + \sum \text{Taxes}$ sur EUR, USD, TND, JPY (arrondi bancaire). \texttt{shopping.utils.test.js} contrôle le filtrage compagnies et le formatage des fenêtres ISO 8601. Je n'ai pas la même densité de tests sur le terminal cryptique ni sur les imports de profils.

\section{Mesures en production}

Les taux d'échec NDC viennent des événements Sentry et des logs Winston sur \texttt{api-aerial}, filtrés sur les actions de type création d'ordre. On a exclu les indisponibilités clairement identifiées côté transporteur (timeouts, HTTP 5xx amont). Sur cette définition, avant les correctifs d'appairage, environ 8,4\,\% des créations d'ordre NDC échouaient pour des raisons applicatives (PaxRefID, services orphelins). Après déploiement, nous sommes restés sous 0,1\,\%. Ce n'est pas une étude statistique formelle : le mix de compagnies a bougé, et le volume n'est pas constant d'un mois sur l'autre.

Pour les paniers encore associés à une offre après un HTTP 409, nous avons compté, sur la période observée dans les logs front, ceux qui aboutissaient à une émission via la modale --- de l'ordre de 92\,\%. Les cas sans nouvelle offre (vol fermé) n'entrent pas dans ce dénominateur.

La latence de recherche (4,2\,s puis 3,0\,s en moyenne) a été mesurée lors de campagnes de tests internes, sur 10\,000 requêtes multi-fournisseurs, pas sur l'intégralité du trafic production. Sur deux ans d'exploitation suivie, nous n'avons pas relevé d'ADM pour double écriture passive Sabre/Amadeus après le découplage POS.
